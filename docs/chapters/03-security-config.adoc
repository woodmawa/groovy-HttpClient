[[security-config]]
= Security Configuration

== Overview

The `SecurityConfig` class is the cornerstone of the Groovy HTTP Client's security model. It provides a declarative, environment-aware approach to configuring TLS policies, timeout controls, SSRF protection, cookie handling, and resilience patterns.

`new GroovyHttpClient("https://...")` uses `SecurityConfig.defaults(baseUrl)`, which is safe to use as-is: verified TLS, no absolute URLs, policy-checked redirects and no automatic retries. For production code, choose the profile that matches your environment (or build exactly what you need with `GroovyHttpClient.builder(...)`) and pass it to the constructor, so the decision is visible in your code.

NOTE: Before 2.0.0 the String constructor used the `testing()` profile, which accepted any certificate. See <<upgrading-2>>.

[IMPORTANT]
====
Security is not an add-on in this library—it's baked into the foundation. Every `GroovyHttpClient` instance requires a `SecurityConfig`, ensuring security decisions are explicit and auditable.
====

=== Design Goals

[horizontal]
*Environment Awareness*:: Different security needs for production vs. testing
*Fail-Safe Defaults*:: Secure by default, insecure by opt-in  
*Configuration as Code*:: Security policies version-controlled alongside application code
*Zero Runtime Magic*:: No classpath scanning, no reflection-based configuration loading
*Immutability*:: Configuration cannot be changed after creation, preventing drift

== Configuration Profiles

`SecurityConfig` provides five built-in profiles optimized for different environments.

.Profiles at a glance
[cols="1,1,1,1,1,1"]
|===
|Profile |Certificates verified |TLS |Absolute URLs |Automatic retry |Use for

|`defaults()`   |yes |1.3, 1.2 |no  |none |the String constructor; general use
|`production()` |yes |1.3      |no  |idempotent methods, 3 attempts |production services
|`staging()`    |yes |1.3      |no  |as production |pre-production, with logging
|`testing()`    |yes (optionally against your own `SSLContext`) |1.3, 1.2 |yes, to allowed hosts |none |tests against local / mock servers
|`trustAll()`   |*no* |1.3, 1.2 |yes, to allowed hosts |idempotent methods, 2 attempts |local debugging only
|===

=== Default Profile

Used by `new GroovyHttpClient(baseUrl)`:

[source,groovy]
----
def client = new GroovyHttpClient("https://api.example.com")
// same as
def client2 = new GroovyHttpClient(SecurityConfig.defaults("https://api.example.com"))
----

Certificates and host names are verified against the JVM trust store, TLS 1.3 and 1.2 are allowed, absolute URLs are refused, cookies are accepted only from the original server, redirects are followed (up to 5 hops) only to allowed hosts, responses are capped at 10 MB, and nothing is retried automatically.

=== Production Profile

The production profile enforces the strictest security controls:

[source,groovy]
----
def config = SecurityConfig.production("https://api.example.com")

def client = new GroovyHttpClient(config)
----

.Production Profile Settings
[cols="2,3,2"]
|===
|Property |Value |Rationale

|`insecureAllowed`
|`false`
|Only verified TLS connections

|`enforceHostnameVerification`  
|`true`
|Prevent MITM attacks

|`allowedTlsProtocols`
|`["TLSv1.3"]`
|Latest secure protocol only

|`allowAbsoluteUrls`
|`false`  
|SSRF protection

|`cookiePolicy`
|`ACCEPT_ORIGINAL_SERVER`
|Prevent cookie injection

|`maxResponseBytes`
|`10,000,000` (10 MB)
|DoS protection

|`connectTimeout`
|`5 seconds`
|Fail fast on network issues

|`requestTimeout`
|`20 seconds`
|Prevent hung connections

|`failureThreshold`
|`5`
|Circuit breaker sensitivity

|`retryPolicy`
|Enabled (3 attempts) for idempotent methods
|Automatic recovery from I/O errors, timeouts and 5xx, without re-sending POST or PATCH
|===

WARNING: Production profiles never trust unverified certificates. A server with a private-CA or self-signed certificate needs that CA in the JVM trust store, or an `SSLContext` built from it: `withOverrides(sslContext: myContext)`.

=== Staging Profile

Staging mirrors production but with enhanced observability:

[source,groovy]
----
def config = SecurityConfig.staging("https://staging.api.example.com")
----

.Differences from Production
* `enableLogging = true` — Request/response logging enabled
* `requestTimeout = 30 seconds` — Allows longer debugging sessions
* Same security controls as production

TIP: Use staging profiles to validate security policies before production deployment.

=== Testing Profile

The testing profile relaxes host and cookie rules for unit and integration tests, but still verifies TLS certificates:

[source,groovy]
----
def config = SecurityConfig.testing("http://localhost:8080")
def client = new GroovyHttpClient(config)

// HTTPS test server with a self-signed certificate: trust exactly that certificate
SSLContext testTls = SSLContext.getInstance("TLS")
testTls.init(null, TrustManagerFactory.getInstance("PKIX").with {
    def ks = KeyStore.getInstance("PKCS12")
    new File("src/test/resources/test-truststore.p12").withInputStream { ks.load(it, "changeit".toCharArray()) }
    init(ks)
    trustManagers
}, null)

def tlsClient = new GroovyHttpClient(SecurityConfig.testing("https://localhost:8443", testTls))
----

.Testing Profile Settings
[cols="2,3"]
|===
|Property |Value

|`insecureAllowed`
|`false` — certificates are verified (pass an `SSLContext` to trust a test certificate)

|`allowAbsoluteUrls`
|`true` — absolute URLs are accepted, but only to hosts in `allowedHosts` (by default the base URL's host)

|`cookiePolicy`
|`ACCEPT_ALL` — Simplified cookie handling

|`retryPolicy`
|Disabled by default (1 attempt)

|`enableLogging`  
|`true` — Full request/response visibility

|`enableMetrics`
|`false` — Reduced overhead
|===

[CAUTION]
====
*Don't use the testing profile in production.* It accepts cookies from any server and does no retries. (Before 2.0.0 it also accepted any certificate; it no longer does.)
====

=== Trust-All Profile

The most permissive profile for local development and debugging:

[source,groovy]
----
def config = SecurityConfig.trustAll("http://localhost:3000")
----

This profile disables:

* TLS certificate validation
* Hostname verification

It is the *only* profile that does. Host allow-listing still applies: absolute URLs and redirects can only reach hosts in `allowedHosts`. A WARN is logged whenever a client is built with it.

[WARNING]
====
The `trustAll()` profile should *only* be used for:

* Local development against `localhost`
* Debugging TLS issues
* Throwaway proof-of-concept code

It must never be used in production, staging, or any network-accessible environment.
====

== Custom Configuration

All profiles can be customized using `withOverrides()`. An explicitly supplied value always wins, including `false` and `0` (before 2.0.0, `allowRedirects: false` and `enableMetrics: false` were silently ignored). Overriding `baseUrl` without supplying `allowedHosts` re-derives the allow-list from the new host:

[source,groovy]
----
def config = SecurityConfig.production("https://api.example.com")
    .withOverrides([
        requestTimeout: Duration.ofSeconds(60),
        enableLogging: true,
        failureThreshold: 3,
        allowedHosts: ["api.example.com", "cdn.example.com"] as Set
    ])
----

=== Available Properties

.Core Settings
[cols="2,2,3"]
|===
|Property |Type |Description

|`baseUrl`
|`String`  
|Root URL for all requests

|`connectTimeout`
|`Duration`
|TCP handshake timeout

|`requestTimeout`
|`Duration`
|Per-request timeout (entire request/response cycle)

|`maxResponseBytes`
|`Long`
|Maximum response body size. The download is cancelled as soon as it is crossed and `HttpResponseException` with status 413 is raised. Must be > 0; use `Long.MAX_VALUE` for no limit.

|`allowRedirects`
|`Boolean`
|Follow redirects. When `false`, the 3xx response is returned to you.

|`maxRedirects`
|`Integer`
|Maximum redirect hops (default 5); more raises `RedirectRejectedException`
|===

[[redirect-policy]]
=== Redirect Policy

Redirects are followed by the client itself, never by the JDK, so every hop is checked:

* the target host must be in `allowedHosts` (the base URL's host is always included);
* only `http` and `https` targets are followed, and HTTPS is never downgraded to HTTP;
* `Authorization`, `Proxy-Authorization` and `Cookie` headers are dropped when the redirect changes scheme, host or port;
* `303`, and `301`/`302` after a `POST`, are followed as `GET` without a body; `307` and `308` keep the method and body.

A refused redirect raises `GroovyHttpClient.RedirectRejectedException`.

.Security Settings
[cols="2,2,3"]
|===
|Property |Type |Description

|`insecureAllowed`
|`Boolean`
|Allow self-signed certificates (trust-all mode)

|`enforceHostnameVerification`
|`Boolean`  
|Verify TLS certificate hostname matches target

|`allowedTlsProtocols`
|`List<String>`
|Permitted TLS protocol versions

|`allowedCipherSuites`
|`List<String>`
|Permitted cipher suites (empty = JVM defaults)

|`trustStore`
|`KeyStore`
|Trust exactly these certificates (private CA, self-signed server) with full verification

|`trustManagers`
|`TrustManager[]`
|Alternative to `trustStore`

|`keyManagers`
|`KeyManager[]`
|Client certificate(s) for mutual TLS; combine with `trustStore`, or omit it to trust the JVM defaults

|`sslContext`
|`SSLContext`
|A complete SSLContext instead of the three settings above. Null = JVM default.
|===

None of the trust settings can be combined with `insecureAllowed`, and `sslContext` cannot be combined with the other three. Unknown setting names are refused with `IllegalArgumentException`.

NOTE: `trustStore`, `trustManagers` and `keyManagers` take effect from 2.0.0. In 1.x they were silently ignored. See the SSL certificate guide in the repository for keystore recipes.

[source,groovy]
----
// private CA + mutual TLS
def client = GroovyHttpClient.builder("https://mtls.internal.example")
        .trustStore(companyCaStore)
        .keyManagers(clientCertKeyManagers)
        .build()
----

.Security Settings (continued)
[cols="2,2,3"]
|===
|Property |Type |Description

|`enforceHostnameVerification`
|`Boolean`
|See above (repeated here for reference): keep `true` with custom trust material too

|`allowAbsoluteUrls`
|`Boolean`
|Allow requests to absolute URLs outside `baseUrl`

|`allowedHosts`
|`Set<String>`
|Host allow-list for SSRF protection, applied to absolute URLs and to every redirect hop. Matching is case-insensitive and ignores a trailing dot.

|`cookiePolicy`
|`CookiePolicy`
|Cookie acceptance policy
|===

.Resilience Settings
[cols="2,2,3"]
|===
|Property |Type |Description

|`failureThreshold`
|`Integer`
|Failures before circuit breaker opens

|`resetTimeoutMs`
|`Long`
|Circuit breaker reset delay (milliseconds)

|`retryPolicy`
|`RetryPolicy`
|Retry configuration (attempts, backoff, conditions)
|===

.Observability Settings
[cols="2,2,3"]
|===
|Property |Type |Description

|`enableLogging`
|`Boolean`
|Log requests and responses

|`enableMetrics`
|`Boolean`
|Collect request metrics (future feature)
|===

== TLS Configuration

=== Protocol Selection

Specify allowed TLS versions:

[source,groovy]
----
def config = SecurityConfig.production("https://api.example.com")
    .withOverrides([
        allowedTlsProtocols: ["TLSv1.3", "TLSv1.2"]
    ])
----

[cols="2,3"]
|===
|Protocol |Recommendation

|`TLSv1.3`
|Preferred — modern, secure, performant

|`TLSv1.2`
|Acceptable — widely supported

|`TLSv1.1`, `TLSv1.0`  
|Deprecated — should not be used

|`SSLv3`, `SSLv2`
|Insecure — never use
|===

=== Cipher Suite Control

Restrict cipher suites (empty list = JVM defaults):

[source,groovy]
----
def config = SecurityConfig.production("https://api.example.com")
    .withOverrides([
        allowedCipherSuites: [
            "TLS_AES_256_GCM_SHA384",
            "TLS_AES_128_GCM_SHA256"
        ]
    ])
----

NOTE: Cipher suite names are Java-specific. Use `SSLContext.getDefault().getSupportedSSLParameters().getCipherSuites()` to list available suites.

=== Hostname Verification

Control whether TLS certificate hostnames must match:

[source,groovy]
----
// Production: hostname verification required
def prod = SecurityConfig.production("https://api.example.com")

// Testing: hostname verification disabled
def test = SecurityConfig.testing("https://api.example.com")
    .withOverrides([
        enforceHostnameVerification: false
    ])
----

[WARNING]
====
Disabling hostname verification opens you to man-in-the-middle attacks. Only disable for:

* Testing against hosts with wrong SANs
* Local development environments
* Debugging TLS issues

Never disable in production.
====

== SSRF Protection

Server-Side Request Forgery (SSRF) protection prevents attackers from making your server call arbitrary URLs.

=== Host Allow-Listing

Restrict which hosts the client can contact:

[source,groovy]
----
def config = SecurityConfig.production("https://api.example.com")
    .withOverrides([
        allowAbsoluteUrls: true,
        allowedHosts: [
            "api.example.com",
            "cdn.example.com",
            "auth.example.com"
        ] as Set
    ])

def client = new GroovyHttpClient(config)

// ✅ Allowed
client.getSync("https://api.example.com/data")  

// ❌ Throws IllegalArgumentException
client.getSync("https://evil.com/steal-data")
----

The same allow-list is applied to every redirect hop, so an allowed host cannot bounce the client somewhere else. See <<redirect-policy>>.

[IMPORTANT]
====
The `baseUrl` host is *automatically* added to `allowedHosts`. You only need to list additional trusted hosts.
====

=== Absolute URL Control

Disable absolute URLs entirely for maximum protection:

[source,groovy]
----
def config = SecurityConfig.production("https://api.example.com")
    .withOverrides([
        allowAbsoluteUrls: false
    ])

def client = new GroovyHttpClient(config)

// ✅ Allowed (relative to baseUrl)
client.getSync("/users")

// ❌ Throws IllegalArgumentException
client.getSync("https://api.example.com/users")
----

TIP: For microservices communicating with a single API, set `allowAbsoluteUrls = false` to eliminate SSRF risk entirely.

== Cookie Policies

Configure how cookies are handled using Java's `CookiePolicy`:

[source,groovy]
----
import java.net.CookiePolicy

def config = SecurityConfig.production("https://api.example.com")
    .withOverrides([
        cookiePolicy: CookiePolicy.ACCEPT_ORIGINAL_SERVER
    ])
----

.Available Cookie Policies
[cols="2,3"]
|===
|Policy |Behavior

|`ACCEPT_ALL`
|Accept all cookies from any domain

|`ACCEPT_NONE`
|Reject all cookies

|`ACCEPT_ORIGINAL_SERVER`  
|Only accept cookies from the origin server (default for production)
|===

NOTE: The cookie policy works in conjunction with the automatic `CookieManager`. See <<cookies,Cookie Management>> for usage examples.

== Timeout Configuration

Proper timeout configuration is critical for application stability.

=== Connection Timeout

Time allowed for TCP handshake:

[source,groovy]
----
def config = SecurityConfig.production("https://api.example.com")
    .withOverrides([
        connectTimeout: Duration.ofSeconds(3)
    ])
----

* *Too Low*: False failures on slow networks
* *Too High*: Slow failure detection, resource exhaustion
* *Recommended*: 3-10 seconds for production

=== Request Timeout

Total time for complete request/response cycle:

[source,groovy]
----
def config = SecurityConfig.production("https://api.example.com")
    .withOverrides([
        requestTimeout: Duration.ofSeconds(30)
    ])
----

* *Too Low*: Fails legitimate slow requests (large payloads, slow APIs)
* *Too High*: Hung connections, cascading failures
* *Recommended*: 20-60 seconds depending on use case

A single request can override it from the DSL:

[source,groovy]
----
client.getSync("/report") {
    timeout(Duration.ofMinutes(2))   // this request only
}
----

NOTE: Before 2.0.0 a per-request `timeout(...)` was silently ignored.

[TIP]
====
Set timeout values based on your API's P99 latency:

* Fast APIs (<100ms P99): 10-20 seconds
* Medium APIs (100-500ms P99): 20-40 seconds  
* Slow APIs (>500ms P99): 40-60 seconds

Never set infinite timeouts in production.
====

== Retry Policy Configuration

Configure automatic retry behavior for transient failures.

=== Basic Retry Setup

[source,groovy]
----
import org.softwood.http.GroovyHttpClient.RetryPolicy

def retryPolicy = new RetryPolicy.Config().with {
    maxAttempts(3)
    backoffExponential(200, 2000, true) // initial, max, jitter
    onIoExceptions(true)
    onTimeouts(true)
    on5xx(true)
    build()
}

def config = SecurityConfig.production("https://api.example.com")
    .withOverrides([
        retryPolicy: retryPolicy
    ])
----

=== Retry Configuration Options

.RetryPolicy.Config Methods
[cols="2,3"]
|===
|Method |Description

|`maxAttempts(int)`
|Total attempts including original (1 = no retries)

|`backoffExponential(long, long, boolean)`  
|Configure exponential backoff: initial delay (ms), max delay (ms), jitter enabled

|`onIoExceptions(boolean)`
|Retry on I/O exceptions (connection failures, etc.)

|`onTimeouts(boolean)`
|Retry on timeout exceptions

|`on5xx(boolean)`
|Retry on HTTP 5xx server errors

|`onStatusCodes(Collection<Integer>)`
|Retry on specific status codes

|`retryNonIdempotent(boolean)`
|Also retry POST, PATCH and CONNECT. Off by default.
|===

Retries apply to idempotent methods only (GET, HEAD, OPTIONS, PUT, DELETE, TRACE) unless the policy calls `retryNonIdempotent(true)`. A POST whose response was lost may already have been processed by the server, and sending it again can duplicate the action.

NOTE: Before 2.0.0, status-code retries (`on5xx`, `onStatusCodes`) never fired, and I/O and timeout retries applied to every method. Both are fixed in 2.0.0.

=== Retry Strategies

*Exponential Backoff with Jitter*:

[source,groovy]
----
// Initial: 100ms, doubles each attempt with random jitter
// Max delay: 5 seconds
backoffExponential(100, 5000, true)
----

*Fixed Delay*:

[source,groovy]
----
// Always wait 1 second between attempts
backoffExponential(1000, 1000, false)
----

*No Retries*:

[source,groovy]
----
RetryPolicy.none() // or maxAttempts(1)
----

=== Per-Request Retry Override

Override retry policy for specific requests:

[source,groovy]
----
client.get("/report") {
    retry {
        maxAttempts(5)
        backoffExponential(500, 10000, true)
        on5xx(true)
    }
}

// A POST is retried only with an explicit opt-in -- pair it with an idempotency key
client.post("/payments", payload) {
    header("Idempotency-Key", UUID.randomUUID().toString())
    retry {
        maxAttempts(3)
        on5xx(true)
        retryNonIdempotent(true)
    }
}
----

[WARNING]
====
Only opt in with `retryNonIdempotent(true)` when the server de-duplicates repeated requests (for example by an `Idempotency-Key`). Otherwise a retry can double-charge or create duplicate records.
====

== Circuit Breaker Configuration

Protect your application from cascading failures with circuit breakers.

=== Basic Configuration

[source,groovy]
----
def config = SecurityConfig.production("https://api.example.com")
    .withOverrides([
        failureThreshold: 5,        // Open after 5 failures
        resetTimeoutMs: 30_000L     // Wait 30s before half-open
    ])
----

=== Circuit Breaker States

[plantuml, circuit-breaker-states, svg]
----
@startuml
[*] --> CLOSED : Initial state
CLOSED --> OPEN : Failures >= threshold
OPEN --> HALF_OPEN : Reset timeout elapsed
HALF_OPEN --> CLOSED : Probe succeeds
HALF_OPEN --> OPEN : Probe fails
@enduml
----

.State Descriptions
[cols="1,3"]
|===
|State |Behavior

|*CLOSED*
|Normal operation. All requests proceed. Failures are counted.

|*OPEN*  
|Circuit tripped. All requests immediately fail. No calls to downstream service.

|*HALF_OPEN*
|Testing phase. Exactly one probe request is let through; every other caller gets `CircuitOpenException` until it resolves. Success → CLOSED, Failure → OPEN.
|===

NOTE: Before 2.0.0, HALF_OPEN let every caller through at once.

=== Tuning Guidance

[cols="2,3"]
|===
|Scenario |Configuration

|High-traffic API
|`failureThreshold: 10+`, `resetTimeoutMs: 60000`

|Low-traffic API
|`failureThreshold: 3-5`, `resetTimeoutMs: 30000`

|Flaky service
|`failureThreshold: 15+`, `resetTimeoutMs: 120000`

|Critical path
|`failureThreshold: 2-3`, `resetTimeoutMs: 10000`
|===

NOTE: Circuit breaker state is per-client instance. If you create multiple `GroovyHttpClient` instances, each has its own circuit breaker.

== Response Size Limits

Protect against memory exhaustion from large responses:

[source,groovy]
----
def config = SecurityConfig.production("https://api.example.com")
    .withOverrides([
        maxResponseBytes: 5_000_000L  // 5 MB limit
    ])
----

The client counts bytes as the body arrives and cancels the download as soon as the limit is crossed, so an oversized or endless response never ends up in memory. The request fails with `HttpResponseException` and status 413 (a locally generated status -- the server sent whatever it sent):

[source,groovy]
----
try {
    client.getSync("/large-file")
} catch (GroovyHttpClient.HttpResponseException e) {
    if (e.statusCode == 413) {
        println "Response too large"
    }
}
----

[TIP]
====
Set `maxResponseBytes` based on your use case:

* APIs returning small JSON/XML: 1-10 MB
* File downloads: 100-500 MB or `Long.MAX_VALUE`  
* Streaming APIs: Use streaming APIs, not HTTP client
====

== Observability

=== Logging

Enable request/response logging:

[source,groovy]
----
def config = SecurityConfig.production("https://api.example.com")
    .withOverrides([
        enableLogging: true
    ])
----

Each request logs one INFO line with the method, URL, status, elapsed time and attempt number. Retries and followed redirects also get a line each. For example:

----
[GroovyHttpClient] GET https://api.example.com/users/42 -> 200 in 38 ms (attempt 1)
----

[IMPORTANT]
====
Logged URLs omit the query string and any user-info, and headers and bodies are never logged, because all of these routinely carry credentials and tokens. (Before 2.0.0, `enableLogging` had no effect.)
====

NOTE: Logging uses SLF4J under the logger name `org.softwood.http.GroovyHttpClient`. The library ships no logging backend -- configure yours (Logback, Log4j2) to control output.

=== Metrics

Metrics collection (future feature):

[source,groovy]
----
def config = SecurityConfig.production("https://api.example.com")
    .withOverrides([
        enableMetrics: true
    ])
----

Planned metrics include:

* Request count, rate
* Response time distributions
* Error rates by status code
* Circuit breaker state durations
* Retry attempt counts

[NOTE]
====
Metrics support is planned for a future release. The API is included now for forward compatibility.
====

== Best Practices

=== Environment-Based Configuration

Use different configs per environment:

[source,groovy]
----
class AppConfig {
    static SecurityConfig httpConfig() {
        def env = System.getenv("APP_ENV") ?: "production"
        
        switch (env) {
            case "production":
                return SecurityConfig.production(getApiUrl())
                    .withOverrides([
                        failureThreshold: 5,
                        retryPolicy: productionRetryPolicy()
                    ])
                    
            case "staging":
                return SecurityConfig.staging(getApiUrl())
                
            case "test":
                return SecurityConfig.testing("http://localhost:8080")
                
            default:
                throw new IllegalStateException("Unknown environment: $env")
        }
    }
    
    private static RetryPolicy productionRetryPolicy() {
        new RetryPolicy.Config().with {
            maxAttempts(3)
            backoffExponential(200, 2000, true)
            on5xx(true)
            onTimeouts(true)
            build()
        }
    }
    
    private static String getApiUrl() {
        System.getenv("API_URL") ?: "https://api.example.com"
    }
}
----

=== Configuration Validation

Validate configuration at application startup:

[source,groovy]
----
def config = SecurityConfig.production(apiUrl)

// Validate configuration makes sense
assert config.connectTimeout < config.requestTimeout : 
    "Connect timeout must be less than request timeout"
    
assert config.failureThreshold > 0 : 
    "Failure threshold must be positive"
    
assert !config.insecureAllowed : 
    "Insecure TLS not allowed in production"
----

=== Security Checklist

Before deploying to production, verify:

* [ ] `insecureAllowed = false`
* [ ] `enforceHostnameVerification = true`
* [ ] `allowedTlsProtocols = ["TLSv1.3"]` or `["TLSv1.3", "TLSv1.2"]`
* [ ] `allowAbsoluteUrls` and `allowedHosts` configured appropriately
* [ ] `maxResponseBytes` set to reasonable limit
* [ ] Timeouts configured based on API characteristics
* [ ] Circuit breaker thresholds tuned for traffic patterns
* [ ] Retry policy safe for non-idempotent operations
* [ ] Configuration externalized (environment variables, config files)
