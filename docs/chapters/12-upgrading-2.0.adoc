[[upgrading-2]]
= Upgrading to 2.0

2.0.0 moves the library to Groovy 6 and a Java 25 baseline, and fixes the findings of a security review of 1.0.2. Several fixes change behaviour you may rely on, so read this chapter before upgrading.

== Requirements

[cols="1,1,1"]
|===
| |1.x |2.0

|Java runtime |21+ |*25+* (bytecode targets Java 25; tested on JDK 25 and 27)
|Groovy |5.x |*6.0+*
|Logging backend |`logback-classic` shipped with the library |*none* -- add your own SLF4J 2.x binding
|===

[source,groovy,subs="attributes+"]
----
dependencies {
    implementation '{project-group}:{project-artifact}:{project-version}'
    runtimeOnly 'ch.qos.logback:logback-classic:1.6.5'   // or any SLF4J binding you already use
}
----

== New: HTTP/3

On JDK 26+ the client can use HTTP/3 (QUIC): `builder(url).http3()`, `withOverrides(http3Discovery: ...)` or per request `{ http3() }`. It is off by default, so nothing changes unless you ask for it. On JDK 25 a request for HTTP/3 falls back to HTTP/2. See <<http3>>.

== Behaviour Changes

=== The String constructor verifies TLS certificates

[cols="1,1"]
|===
|1.x |2.0

|`new GroovyHttpClient(url)` used `SecurityConfig.testing(url)`, which *accepted any certificate*
|it uses `SecurityConfig.defaults(url)`: certificates and host names are verified
|===

*What to do:* nothing, for public HTTPS endpoints. For a server with a private-CA or self-signed certificate, trust exactly that certificate:

[source,groovy]
----
def client = GroovyHttpClient.builder("https://internal.example")
        .sslContext(sslContextFromYourTrustStore)
        .build()
----

=== `testing()` verifies certificates; only `trustAll()` doesn't

`SecurityConfig.testing(url)` no longer disables certificate checks. Tests against plain `http://localhost` are unaffected. For a self-signed HTTPS test server, pass an `SSLContext`, `SecurityConfig.testing(url, testSslContext)`, or use `SecurityConfig.trustAll(url)` deliberately.

=== Trust stores and client certificates take effect; unknown settings are refused

The `trustStore`, `trustManagers` and `keyManagers` settings shown in the SSL certificate guide were silently ignored in 1.x, so private-CA and mutual-TLS setups fell back to the JVM trust store. They now take effect (`GroovyHttpClient.builder(...)` also has `.trustStore(...)` and `.keyManagers(...)`).

`SecurityConfig` now refuses setting names it doesn't know, e.g. `withOverrides(allowRedirect: false)`, with `IllegalArgumentException`. In 1.x a typo silently left the default in place.

=== Explicit `false` / `0` settings are honoured

In 1.x, `allowRedirects(false)`, `enableMetrics(false)` and `withOverrides(allowRedirects: false)` were silently turned back into `true`. They now take effect. If a client of yours relied on redirects being followed despite `allowRedirects(false)`, remove that setting.

`withOverrides(baseUrl: ...)` now re-derives `allowedHosts` from the new base URL unless you also pass `allowedHosts`. `maxResponseBytes` must be > 0 (use `Long.MAX_VALUE` for no limit).

=== Redirects are policy-checked

Redirects are now followed by the client itself, not by the JDK:

* targets outside `allowedHosts` are refused with `RedirectRejectedException`, as are HTTPS -> HTTP and more than `maxRedirects` hops (default 5);
* `Authorization`, `Proxy-Authorization` and `Cookie` are dropped when a redirect changes origin.

*What to do:* if you call an API that redirects to another host (a CDN, a login domain), add that host to `allowedHosts`. See <<redirect-policy>>.

=== `*Sync` methods throw the underlying exception

[cols="1,1"]
|===
|1.x |2.0

|`getSync(...)` threw `ExecutionException`; the real error was its `cause`
|`getSync(...)` throws `HttpResponseException`, `HttpTimeoutException`, `IOException`, `CircuitOpenException` or `RedirectRejectedException` directly; `TimeoutException` if the sync wait itself expires
|===

*What to do:* replace `catch (ExecutionException e) { ... e.cause ... }` around sync calls with catches for the real types. The async methods are unchanged: their futures still complete exceptionally and `future.get()` still wraps in `ExecutionException`.

=== `HttpResponseException` keeps the body out of its message

The message now carries the status and at most a 120-character snippet. The full body is `e.responseBody`. Code that parsed `e.message` for the body should read `e.responseBody`.

=== Retries

* Status-code retries (`on5xx`, `onStatusCodes`) now actually happen. In 1.x they never fired, so a policy with `on5xx(true)` sends more requests than before.
* POST, PATCH and CONNECT are no longer retried unless the policy calls `retryNonIdempotent(true)`. This includes `postMultipart`. `production()` therefore retries only GET, HEAD, OPTIONS, PUT, DELETE and TRACE.
* Backoff no longer occupies a sleeping thread.

=== Interceptors see 4xx and 5xx responses

The `HttpResponseException` for status >= 400 is raised after retries, outside the interceptor chain. An interceptor's `next.call(ctx)` therefore completes normally with the 4xx/5xx response. Interceptors that counted errors from the exceptional path should also check `response.statusCode`.

Interceptors run in the order they were added (first added = outermost). That has always been the behaviour; the 1.x documentation said the opposite.

=== The request DSL

* `timeout(...)` in the request closure now takes effect (in 1.x it was silently dropped).
* `version(...)`, `expectContinue(...)` and `setHeader(...)` are explicit DSL methods.
* Any other call inside the closure throws `MissingMethodException`. In 1.x it was forwarded to an internal builder that was never sent.

=== Validation

* Cookie names and values set through `cookie(...)`, `cookies(...)` or `cookieHandler.addCookie(...)` must be valid RFC 6265 tokens / cookie-octets; otherwise `IllegalArgumentException`.
* Multipart `name`, `filename` and `contentType` containing CR, LF or NUL are rejected; `"` is percent-encoded.

=== Circuit breaker

HALF_OPEN admits exactly one probe request; concurrent callers receive `CircuitOpenException` until the probe resolves. In 1.x every caller went through.

=== Logging

`enableLogging(true)` now logs one INFO line per request, plus one per retry and per followed redirect. Lines carry the method, the URL without its query string, the status and the timing; headers and bodies are never logged. In 1.x the flag did nothing.

=== Lifecycle

`close()` now also shuts down the underlying `java.net.http.HttpClient`. It waits up to 5 seconds for in-flight exchanges, then forces the shutdown.

=== Packaging

The `org.softwood.testScripts` scratch classes are no longer in the published jar.

== Checklist

. Java 25+ and Groovy 6 on the classpath; add an SLF4J binding.
. Search for `catch (ExecutionException` around `*Sync` calls.
. Search for `e.message` on `HttpResponseException` where you wanted the body.
. List any cross-host redirect targets in `allowedHosts`.
. Review retry policies: decide per POST/PATCH whether `retryNonIdempotent(true)` is safe.
. HTTPS endpoints with private certificates: supply an `SSLContext`.
. Run your tests: anything that only passed because certificates weren't checked will now fail, which is the point.
