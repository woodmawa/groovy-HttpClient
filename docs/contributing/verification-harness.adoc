= Feature verification harness
:toc:

Every public capability of groovy-HttpClient is listed in one catalogue, every spec says which capabilities it
proves, and a release is gated on each one passing on every protocol it claims, on both supported JDKs.

== The pieces

[cols="1,3"]
|===
| `src/test/resources/feature-catalogue.groovy` | The list of capabilities: id, title, `implemented` or `planned`, the release, the docs chapter, whether a real-server spec is required and on which protocols, and `minJdk` for features that only exist on newer runtimes (HTTP/3: 26).
| `@Feature('area.name')` | On a spec class (every feature method) or a single feature method. Ids must exist in the catalogue.
| `FeatureResultsExtension` | Spock global extension. For each iteration it writes feature ids, protocol, JDK and outcome to `build/feature-results/<task>/<Spec>.jsonl`.
| `src/integrationTest` | Real-server specs. `FeatureServer` is one Jetty 12.1 server per test JVM: TLS with ALPN (h2, http/1.1), cleartext HTTP/1.1, and QUIC/HTTP/3 on JDK 26+.
| `FeatureCoverageSpec` | Static gate: unknown ids, implemented features with no spec, integration features with no real-server spec, untagged spec methods.
| `featureReport` / `featureGate` | The matrix (`build/reports/features/index.html`) and the runtime gate (`build/reports/features/gaps.txt`).
|===

== Tasks

[cols="1,3"]
|===
| `test` / `testJava25` | Unit specs (MockHttpServer) on JDK 27 / JDK 25.
| `integrationTest` / `integrationTestJava25` | Real-server specs plus `FeatureCoverageSpec` on JDK 27 / JDK 25.
| `featureReport` | Renders the matrix from the last run of each test task. Never fails.
| `featureGate` | Fails on a failed iteration, an implemented feature with no pass on a required JDK, or an integration feature with no pass on one of its protocols. HTTP/3 is required on JDK 26+ only.
| `releaseGate` | All of the above, in order. Green here is the release criterion.
|===

== Adding a feature

. Add the catalogue entry with `status: 'planned'` (it shows grey in the report and is never failed).
. Write the unit spec and the real-server spec, tagged with the new id. Real-server specs extend
  `IntegrationSpec` and draw the data variable `protocol` from `Protocol.available()`:
+
[source,groovy]
----
@Feature('compression.gzip-response')
def "a gzip response is decompressed over #protocol"() {
    when:
    def r = client(protocol) { /* builder settings */ }.getSync('/gzip')

    then:
    r.body == FeatureServer.COMPRESSIBLE

    where:
    protocol << Protocol.available()
}
----
. Implement until both are green.
. Flip the entry to `status: 'implemented'` in the same commit. From then on `featureGate` holds it to its
  protocols on both JDKs.
. Document it in the chapter the entry names; the doc examples run in a doc-examples spec.

== FeatureServer endpoints

`/echo` (method, path, query, headers, body and protocol as JSON), `/status/{code}`, `/redirect/{n}?code=`,
`/slow?ms=`, `/bytes?n=`, `/json`, `/xml`, `/gzip`, `/deflate`, `/sse`, `/ndjson`, `/lines`, `/auth/basic`
(`it-user` / `it-pass`), `/auth/bearer` (`it-token`). A forward proxy endpoint arrives with the 2.2 proxy work.

== Traps

* Never start a second HTTP/3 server in the same JVM: quiche crashes the process natively on Windows. Use
  `FeatureServer.get()`; it is stopped by a shutdown hook, never by a spec.
* The test JVMs need `--enable-native-access=ALL-UNNAMED` (set for every `Test` task).
* `@PendingFeature` passes on any failure -- check the red reason before trusting it.
